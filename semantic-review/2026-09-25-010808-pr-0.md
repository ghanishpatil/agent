# Phase 5 autonomy fixes and evaluation integrity

The Phase 5 fixes close the prior verifier-before-evidence path, prevent late verifier output from becoming a verified candidate, validate mutation metadata fail-closed, isolate same-name resources, strengthen the public `SOLVED` field invariant, and add focused regressions for those paths. All 264 tests pass and `compileall` succeeds. The evaluation layer still does not support its held-out and metric claims, and two terminal/public-contract edge cases remain outside the regression suite. The absent baseline and final report are intentionally deferred artifacts and are not behavioral blockers in this pass.

**Watch for:** **confirmed** novel and held-out oracles remain tailored to production specialist probes; **confirmed** several reported rates still count different events than their names imply; **confirmed** a deadline crossed by the final allowed action is reported as `EXHAUSTED`; **confirmed** malformed credential mappings can escape `solve()` as `TypeError`.

**Verdict**: NEEDS_CHANGES

## High-level view

Candidate routing now checks both a `SUPPORTED` hypothesis and current candidate-bound evidence before rewriting an action to the verifier, so hostile pre-evidence candidate proposals are dropped without spending a submission. The post-execution deadline check also prevents a late verifier result from reaching kernel verification.

Mutation updates now require an advanced environment revision, a description, typed context and prerequisite values, and allow-listed tools. Content resources are scoped by resource ID, and the `SolveResult` constructor requires a flag, evidence IDs, and a verification method for `SOLVED`; the exact prior mutation, collision, and result-shape findings are addressed.

The evaluation fixtures still recognize the exact parameter names and decode modes emitted by production specialists. Their labels distinguish known, novel, adversarial, and held-out cases, but the novel/held-out outcomes remain evidence of canned-template regression rather than independent generalization.

Duplicate rejection and stop correctness now use planner diagnostics and expected terminal labels, while recovery episodes are explicitly labeled. The remaining formulas still equate every rejected duplicate with a blind retry, can produce a false-disproof “rate” above 1.0, and treat missing recovery populations as zero performance.

Timeout and input validation are not fully terminal-safe at boundary conditions. The loop records an expired deadline after the last action but falls through to budget exhaustion, while mixed-type credential keys are sorted before the protected orchestration block and raise directly.

## Novel and held-out cases still mirror specialist templates

**Severity: High — confirmed.** The web specialist emits the fixed SSTI probe `name={{7*7}}` (`specialists/web.py:50–53`), and `WebBehaviorAdapter` returns the real flag whenever the query contains `name` (`tests/phase5/support.py:66–85`). The crypto specialist emits the literal `classical` mode (`specialists/crypto.py:64–68`), and the held-out decoder only takes its Caesar path for that exact value (`tests/phase5/support.py:88–111`). The corresponding descriptions also contain the same `name`, template, classical, Caesar, and shift indicators used to select those mechanisms (`tests/phase5/test_evaluation.py:48–53`, `:111–116`).

The anti-memorization assertion proves only that known XOR and held-out Caesar runs use different hypothesis IDs and flags. It does not decouple the held-out oracle from the production action vocabulary or vary parameter discovery, probe shape, artifact interface, or mechanism implementation. Independently authored black-box cases are still required before these results can support a held-out/generalization claim; the current fixtures should remain regression cases.

## Phase 5 rates still conflate distinct events

**Severity: High — confirmed.** Planner duplicate rejections now feed `duplicate_proposals`, which fixes the prior zero-rate blind spot. `observe_planner()` simultaneously increments `blind_retries` by the same count for every duplicate rejection (`autonomy/control.py:91–100`), and the regression explicitly requires blind-retry rate to equal duplicate-action rate (`tests/phase5/test_evaluation.py:239–242`). A proposal rejected before execution is evidence that deduplication worked; it is not necessarily a blind retry, so the two metrics cannot independently measure waste and prevention.

`false_disproofs` counts each wrongly disproven hypothesis but divides by the number of cases (`autonomy/evaluation.py:169–176`, `:222–224`). Because one case may declare multiple `known_correct_hypotheses`, the reported rate can exceed 1.0. Recovery metrics now use explicit episode labels and require later progress, which is a material improvement, but an empty labeled population still returns `0.0` (`:284–309`) rather than unavailable, conflating “not measured” with “measured and never recovered.”

The current metric test exercises only zero false disproofs and locks the duplicate/blind-retry equality in place. Add adversarial metric fixtures with multiple known-correct hypotheses, distinct duplicate and retry events, and empty recovery populations; define denominators and unavailable values before generating the baseline.

## Final-action deadline loses to budget exhaustion

**Severity: Medium — confirmed.** The post-adapter deadline check correctly suppresses candidate creation and records `wall-clock timeout reached after tool execution` (`autonomy/control.py:162–168`, `loop.py:254–271`). After the final permitted action, however, `ReasoningLoop.run()` checks only whether the context is verified and otherwise returns `BUDGET_EXHAUSTED` (`loop.py:101–103`). It never projects the controller’s already-recorded timeout at that boundary.

A direct runtime probe with `max_actions=1` and an adapter that advances the clock beyond the deadline returned `BUDGET_EXHAUSTED` while `controller.terminal_reason` said the wall clock had expired. The existing late-verifier regression uses enough action capacity to enter another iteration, where the timeout is correctly observed, so it misses this terminal precedence case. Re-check the controller deadline before the post-loop budget result and add a one-action regression requiring `TIMEOUT`.

## Credential and nested environment values can bypass `INVALID_INPUT`

**Severity: Medium — confirmed.** `_public_input_errors()` validates scalar challenge fields and the outer tuple shape, but it does not validate credential key/value types or several nested environment members (`autonomy/solver.py:586–637`). `_sanitized_challenge()` preserves any `Mapping` as credentials (`:567`), then `understand_challenge()` sorts its keys before the orchestration `try` block (`autonomy/understanding.py:78`). A `ChallengeInput(description="x", credentials={1: "x", "a": "b"})` therefore raises `TypeError` instead of returning `INVALID_INPUT`; this was reproduced directly.

The same boundary validates only that `permitted_tools` is a tuple, not that its entries are `PermittedTool` instances or that evidence rules, verifier routes, initial state, and prerequisite collections satisfy their declared types. Failures from those nested values occur later inside the broad orchestration block and become `FAILED`, even though the public contract maps input/composition validation errors to `INVALID_INPUT`. Validate nested contract types before `understand_challenge()` and composition, and add malformed credential plus malformed environment-entry regressions.
