# Phase 5 autonomous solver integration and evaluation baseline

Phase 5 composes the specialist brain, planner, trusted adapters, Phase 2 kernel, state controller, and evaluation harness behind a public `solve()` facade. The returned flag path still depends on a kernel candidate with `VerificationStatus.VERIFIED` and global `ControlDecision.STOP`, and the complete 258-test suite plus `compileall` pass. The integration nevertheless leaves blocking gaps in when candidate submissions execute, how wall deadlines are enforced, and whether the benchmark and metrics demonstrate the required held-out behavior. The required final report, reproducible baseline, and protected-tree comparison are also absent, so Phase 2–4 freeze compliance cannot be established from this workspace.

**Watch for:** **confirmed** candidate proposals can call the configured verifier before candidate-bound evidence exists; **confirmed** a tool/verifier that returns after the deadline can still produce `SOLVED`; **confirmed** the nominal novel/held-out fixtures are tailored to the production mechanism templates; **confirmed** several evaluation metrics do not measure the events their names claim; **confirmed** required Phase 5 baseline/freeze artifacts are missing.

**Verdict**: NEEDS_CHANGES

## High-level view

The Phase 2 terminal gate remains structurally intact: `solve()` projects `SOLVED` only from a `VERIFIED` kernel candidate paired with global `STOP`. Specialists receive context, tool names, and memory rather than adapters or kernel mutation APIs; no production challenge-name-to-flag mapping was found.

**Confirmed:** candidate routing can reach the verifier before bound evidence is checked, while wall time is enforced only before dispatch. These asymmetries allow a provenance-free submission attempt and allow a late verifier response to become `SOLVED` after the deadline.

**Confirmed:** mutation handling blocks a missing revision but trusts every other metadata field without schema or consistency checks, including prerequisite changes.

**Confirmed:** nominal novel/held-out fixtures answer the exact probes emitted by the specialist catalog. Duplicate, stop, and recovery metrics also ignore the planner/controller events and ground-truth relationships needed to support their names.

**Confirmed:** malformed runtime inputs do not consistently become `INVALID_INPUT`, `SolveResult` can be constructed as `SOLVED` without verification evidence or method, and same-name content resources overwrite one another.

**Confirmed:** 258 tests and `compileall` pass, but the required final report, baseline JSON, and protected-tree hash comparison are absent. Missing Git metadata also prevents complete diff and byte-identity verification.

## Candidate routing spends verifier attempts before provenance is established

**Severity: High — confirmed.** `RoutedReasoningSource._route()` rewrites every candidate-bearing suggestion to the configured verifier. In `ReasoningLoop._execute_one()`, the adapter executes at `.agent/src/ctf_agent/loop.py:248`; only afterward does the loop collect bound evidence and conditionally create the candidate at lines 263–292. If no evidence is bound, the code comments describe the call as a normal probe, but its tool, target, and input have already been rewritten to the real verifier, and `AutonomyController` counts it as a submission.

The planner also permits candidate-bearing suggestions for any open hypothesis; the supported-hypothesis rule is only an exception that permits submissions after a hypothesis leaves the open set. The default specialists normally derive candidates from observed eligible output, but the typed LLM/specialist boundary is supposed to remain safe even for hostile or malformed proposals. Reject candidate actions before adapter execution unless the candidate has current bound evidence and the source hypothesis is in the permitted submission state; route to the verifier only after that gate succeeds.

## A verifier response can cross the wall deadline and still win

**Severity: High — confirmed.** `AutonomyController` checks elapsed time in `before_iteration()` and `before_action()` (`autonomy/control.py:64` and `:112`), then `ReasoningLoop` performs an unbounded adapter call and kernel transition. There is no deadline check after execution or before candidate verification. If a verifier starts before the limit and returns accepted after it, the kernel records `STOP`; the next loop iteration checks `context.is_verified()` before consulting the controller (`loop.py:79–84`), and `_project_result()` returns `SOLVED`.

This makes `timeout_seconds` a dispatch deadline rather than the documented hard wall-time budget. Pass remaining time into timeout-capable adapters and re-check the deadline immediately after execution, before verification can become terminal. A result that arrives late may be journaled as evidence, but it must not convert the run to `SOLVED` under an expired hard budget.

## The benchmark is coupled to the solver's canned probes

**Severity: High — confirmed.** The production specialists emit fixed probes such as `name={{7*7}}` and decode mode `classical`. The nominal novel SSTI fixture returns the real flag whenever the query contains `name` (`tests/phase5/support.py:78–83`), while the held-out classical fixture returns the flag only for the literal `classical` mode (`support.py:99–103`). Their challenge descriptions explicitly contain the same template/classical indicators used to select those mechanisms.

There is no production challenge-name or hardcoded flag map, which is the right boundary, but these cases still validate recognition of the implementation's own action templates rather than materially held-out reasoning. Add independently authored cases that vary parameter discovery, payload shape, artifact structure, and mechanism while keeping the oracle isolated from planner decisions. Keep template-matched scenarios as regressions, not evidence of held-out generalization.

## Evaluation formulas overstate duplicate, stop, and recovery behavior

**Severity: High — confirmed.** `duplicate_action_rate` counts only executed `ActionTrace` entries with decision `DUPLICATE` (`autonomy/evaluation.py:156–162`), while the planner filters duplicates before they enter `pipeline_results`; the controller's `duplicate_proposals` counter is ignored. `stop_correctness` awards success to every non-`SOLVED` result with no flag (`:213–222`) even when its terminal status is wrong. Dead-end and failure recovery select any result containing a disproven/low-priority hypothesis or failure evidence and call it recovered if the overall case solved, without showing that the solver reopened, bypassed, or recovered that affected branch.

These formulas can report perfect stop behavior and zero duplicate rate without exercising the claimed behavior. Base duplicate rate on rejected duplicate proposals plus attempted actions, compute stop correctness against expected terminal status and post-STOP traces, and label recovery episodes so numerator cases prove progress after the specific dead end or failure. Ground-truth-dependent metrics should be unavailable rather than zero when their labels are absent.

## State reduction trusts malformed mutation metadata

**Severity: Medium — confirmed.** `AutonomyController.after_result()` blocks only when `state_changed=True` lacks a nonempty `state_revision`. Once that string exists, it applies `available_tools`, authentication/session/challenge contexts, and prerequisite additions/removals directly from adapter metadata (`autonomy/control.py:190–224`). It does not validate sequence element types, require the revision to advance, require a state description, or reject inconsistent fields.

Trusted adapters are the correct authority for observations, but malformed adapter output is explicitly part of the Phase 5 failure model and must fail closed. Parse mutation metadata through a typed schema, require a materially new revision plus a mutation description, constrain available tools to the registered allow-list, and block on malformed or contradictory updates before changing prerequisites.

## Public input and terminal contracts are only partially enforced

**Severity: Medium — confirmed.** `solve()` dereferences resources and calls `understand_challenge()` before its `try` block (`autonomy/solver.py:77–78`), while validation compares values without type checks. Malformed public values such as nonnumeric constraints can raise `TypeError` or lead to `FAILED` instead of the documented `INVALID_INPUT`. `SolveResult.__post_init__()` requires only a nonempty flag for `SOLVED` (`autonomy/contracts.py:255–259`), so the exported type accepts a solved result with no verification evidence IDs or final verification method.

Validate public object types, integer budget fields, finite positive timeout, resource tuples, and nested mappings before any dereference, with validation failures projected to `INVALID_INPUT`. Tighten the terminal result invariant so `SOLVED` requires verification evidence and method, and make authoritative result construction internal or require a kernel-derived terminal proof object.

## Same-name content resources overwrite one another

**Severity: Medium — confirmed.** Materialized content uses `Path(filename).name` and writes directly to `workspace/resources/<basename>` (`autonomy/resources.py:26–34`). Distinct resource IDs with the same filename therefore resolve to the same path; the later resource silently overwrites the earlier one, and both returned entries point to the final bytes. That corrupts challenge input identity and can make evidence provenance refer to content other than the caller supplied for that resource.

Reject duplicate normalized filenames or materialize each resource under a unique ID-scoped directory. Record the resulting resource ID-to-path mapping rather than only a tuple of paths.

## Required Phase 5 baseline and freeze evidence are missing

**Severity: High — confirmed.** `phase5.md` requires `.agent/docs/phase5_report.md`, a reproducible baseline, exact metrics/results, and protected-tree verification. Neither `phase5_report.md` nor `phase5_baseline.json` exists, and no Phase 5 before/after hash manifests were found. The workspace also has no `.git` directory, so `git diff main` and revision/dirty-state capture are unavailable.

Generate the mandated report and baseline from the finished evaluation, including all negative results and known weaknesses, and retain the pre/post SHA-256 manifests that prove Phase 2, `.agent_audit`, `.kiro`, and `writeups` are unchanged. Restore or provide repository metadata so the complete local diff can be audited; until then, regression execution is verified but change-scope and byte-identity claims are not.

## Validation coverage leaves the blocking paths untested

**Severity: Medium — confirmed.** The complete suite passes 258 tests and `python -m compileall -q src tests` succeeds. Existing budget tests cover denial before a second execution and timeout before the first execution, but not an adapter that returns after the deadline. Trust tests show an untrusted flag cannot become `SOLVED`, but do not assert that a candidate with no bound evidence never calls the verifier. Evaluation assertions mostly check ranges and the expected synthetic outcomes, so they do not expose the metric denominator problems above.

Add regression tests for zero-evidence candidate proposals with verifier call count zero, verifier completion after deadline, malformed mutation metadata, duplicate resource filenames, malformed public input types, and metric fixtures where terminal status is wrong or duplicates are planner-rejected.
